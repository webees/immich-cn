# 规范与约定

本文合并命名规范、术语规范与文档严谨性规范，是代码与文档的共同约定。

## 命名规范

模块名必须表达单一职责，避免 `utils`、`helpers`、`common`、`misc` 等无边界名称。

| 模块 | 职责 |
|:--|:--|
| `artifact_spec.py` | 制品命名规范与解析 |
| `pipeline.py` | 构建流水线编排 |
| `dataset.py` | 规范 SQLite 数据集 |
| `localization.py` | 中文名称解析 |
| `settings.py` | 配置与上游源定义 |
| `fetching.py` | 下载、缓存与重试 |
| `logging_config.py` | 日志配置 |
| `domain.py` | 领域数据模型 |
| `packaging.py` | 发布制品打包 |
| `display.py` | 展示粒度与组合 |
| `rate_limit.py` | 限速器 |
| `validation.py` | 制品校验 |

- 测试文件名与被测模块对应，例如 `pipeline.py` → `test_pipeline.py`；
- 文件名使用小写 snake_case，不使用版本后缀与 `new`、`final` 等词；
- 发布资产使用 [数据格式与制品命名](data-format.md) 的 v4 规则，不生成兼容别名；
- 运行时占位符 `{admin_2}` 与制品展示粒度 ID `admin2` 是不同契约，前者不改，后者不写回花括号；
- 工作流文件名使用 `<动作>-<领域>.yml`，例如 `update-data.yml`、`cleanup.yml`。

代码标识符：类名用名词（`BuildResult`），函数名用动词短语（`run_build`），布尔值用 `is_`/`has_`/`should_` 前缀，常量用 `UPPER_SNAKE_CASE` 并注明单位或格式，不用 `data`、`info`、`temp`、`value` 作为跨作用域名称。

架构边界：`dataset.py` 是规范数据层，`packaging.py` 是发布适配层，`pipeline.py` 只编排阶段，`providers/` 只处理外部增强，`validation.py` 只校验不修改制品。

## 术语规范

文档以中文为主，只有专有名词、标识符与无通用中文译名的技术缩写保留英文。

保留英文：产品与服务名（`Immich`、`GitHub`、`Docker`、`GHCR`、`GeoNames`、`Natural Earth`、`Nginx`、`PostgreSQL`、`Valkey`、`Trivy`、`Cosign`、`jsDelivr`、`SQLite`、`Alpine`），协议与标准缩写（`API`、`CDN`、`OCI`、`SBOM`、`SLSA`、`EXIF`、`CSP`、`ETag`、`WGS-84`、`GCJ-02`），以及命令、路径、环境变量、字段名、文件名、标签名与状态值等标识符。

|:--|:--|
| `release` | 发布 |
| `artifact` | 制品 |
| `manifest` | 清单 |
| `checksum` | 校验和 |
| `coverage` | 覆盖率 |
| `snapshot` | 快照 |
| `cache` | 缓存 |
| `fingerprint` | 指纹 |
| `image` | 镜像 |
| `digest` | 摘要 |

| `workflow` | 工作流 |

同一篇文档首次出现保留英文的缩写时，可用中文短句解释一次，之后不再反复改写。

## 文档严谨

文档必须区分事实、设计目标、运行条件、验证范围与未验证项，禁止把意图写成保证。

| 类型 | 允许写法 | 禁止写法 |
|:--|:--|:--|
| 已验证事实 | 说明命令、版本、日期、范围与结果 | 只写“已验证”“保证正确” |
| 设计目标 | “按设计”“目标是”“默认路径下” | “完全自动”“永远不会失败” |
| 运行条件 | 明确前提、依赖与失败条件 | 省略 GitHub、上游、权限或网络前提 |
| 未验证项 | “未验证”“尚未覆盖”“需要实测” | 用推测代替证据 |

- H2 使用 4 字左右中文短标题，同组标题尽量保持相同字数；
- 表格必须包含表头与分隔行，各行列数一致，正文不得插入表格中间；
- README 只保留代码许可、构建入口、外部依赖、行政区粒度、发布方式五个维度。

“完全、任何、所有、永远、绝不、始终、唯一、保证、零风险、不会失败”等绝对化词语，只有在范围可枚举、验证方法可复现、例外条件已写出时才可使用。“全自动”在本仓库中作为机制名称使用（徽章、章节标题、机制描述），首次出现处必须写出运行前提，不得改成“保证每天更新”。

### 文档范围

文档只记录当前版本：当前代码、配置、发布资产、行为与验证边界。不得记录非当前版本的内容。只允许两类内容：

| 可以写 | 原因 |
|:--|:--|
| 当前树事实：在哪个提交、用哪条命令核查了哪些路径与关键词、得到什么结果 | 可复现，也可能被反例推翻 |
| 项目声明：本项目按什么方式组织代码与数据，并注明这是声明 | 读者知道它不是被证明的结论 |

推荐写法：

> 本项目按独立实现组织：本仓库当前树中的代码、配置、工作流与数据构建脚本由本项目维护。在文末「致谢」所列同类项目范围内，仓库路径名与生产代码中未发现被引用或打包的代码文件与人工整理数据文件（核查范围、关键词与命令见下文）。文末「致谢」记录了与本项目相关的上游思路来源；对 Immich 文本格式的兼容属于消费端适配。以上均为当前仓库状态与项目声明。

核查方式：在指定提交上按路径名与关键词搜索仓库，并记录命令与结果；结论只覆盖已列出的路径与关键词。
