# ADR 0001：保留 Immich 输出契约，独立演进内部格式

- 状态：已接受
- 日期：2026-10-06
- 决策范围：数据格式、消费者兼容性、内部模型与发布方式

## 背景

Immich 直接从固定路径读取反向地理编码数据。文件名、制表符列位置、行政层级代码和
`geodata-date.txt` 的存在都是运行时契约。这个契约不是 immich-cn 定义的，也不能由
发布方单方面改变。

同时，构建过程需要一个更适合表达复杂层级关系、来源追踪和增量更新的内部模型。
如果把“内部模型”和“Immich 运行时格式”绑死，校验、缓存、开发和发布都会被外部格式限制。

## 决策

1. 外部输出保持 Immich 当前可读取的文件名、目录结构、列位置和语义。
2. 内部使用 `levels.tsv` 表达“地点 → 四级名称”，使用 `patterns.tsv.gz` 表达运行时粒度，
   使用 `manifest.json` 表达来源、统计和制品指纹，使用 JSONL 缓存 provider 结果。
3. CLI、Python API、容器入口和粒度切换属于本项目自己的使用契约，可以独立设计和演进。
4. 如果未来需要新的消费者格式，新增适配器或导出器；不直接替换现有 Immich 输出。

## 原因

- 兼容性是数据产品的首要价值。用户只需替换目录或镜像，不需要修改 Immich 源码。
- Immich 的格式是约束条件，不是设计目标；内部模型可以更规范，但不能替消费者做迁移决定。
- 适配层边界明确后，内部格式可以独立优化，不会把每次优化变成破坏性变更。
- 现有 CLI 和容器已经提供了更好的使用方式：下载、构建、校验、发布、运行时切换都由项目控制。

## 结果

- `geodata.zip`、镜像中的 `geodata/` 以及 `data-*` Release 资产继续可直接使用。
- 内部字段、缓存格式和流水线实现可以重构，只要适配器输出保持稳定。
- 新增格式必须同时提供迁移方案、兼容验证和回滚策略。

## 未选择的方案

### 直接替换为自定义 JSON / SQLite

读写体验可能更好，但官方 Immich 无法直接读取，会迫使所有用户修改服务端代码或维护额外适配器。
这会使“替换数据源”变成一个不可见的大迁移，不符合当前目标。

### 让用户自行转换

把复杂性转嫁给用户，下载后还要运行额外工具，且容易出现列错位、编码错误和版本漂移。
项目已有的数据镜像和 CLI 已经能够在用户侧完成转换，没有必要再增加一层人工步骤。

### 同时发布多套不兼容格式

会增加测试矩阵、文档分支和制品体积，却没有明确消费者。只有在出现第二个真实消费者并有兼容性
预算时，才应增加新的适配器。
